Azure Well-Architected Framework — это набор руководящих принципов, которые можно использовать для повышения качества рабочей инфраструктуры и приложений.

Инструмент для оценки имеющейся инфраструктуры в Azure по принципам заложенных в Microsoft Azure Well-Architected Framework — Microsoft Azure Well-Architected Review.

Обучающий курс на Microsoft Learn на русском — Создавайте отличные решения с помощью Microsoft Azure Well-Architected Framework

Microsoft Azure Well-Architected Framework

  • Фокусировка затрат — Управление затратами для получения максимальной отдачи.
  • Функциональное превосходство — Операционные процессы, которые поддерживают работу системы в рабочем состоянии.
  • Эффективность производительности — Способность системы адаптироваться к изменениям нагрузки.
  • Надёжность — Способность системы восстанавливаться после сбоев и продолжать работать.
  • Безопасность — Защита приложений и данных от угроз.

Фокусировка затрат

При разработке облачного решения сосредоточьтесь на раннем создании дополнительной ценности. Применяйте принципы Build-Measure-Learn(Lean, Цикл Демминга, HADI цикл), чтобы ускорить вывод на рынок, избегая дорогостоящих и долгих решений. Используйте для своей архитектуры распределительную стратегию и инвестируйте в будущее масштабирование, а не в первую версию или громоздкий MVP в надежде крупных инвестиций в будущем. Учитывайте альтернативные издержки в своей архитектуре и баланс между преимуществом первопроходца и «fast follow». Используйте калькуляторы затрат, чтобы оценить начальную стоимость и эксплуатационные расходы. Наконец, установите политики, бюджеты и средства контроля, которые устанавливают пределы затрат для вашего решения.

Функциональное превосходство

Этот компонент охватывает операционные процессы, которые поддерживают работу приложения в производственной среде. Фактически мы говорим про DevOps контур. Развёртывания должны быть надёжными и предсказуемыми. Их следует автоматизировать, чтобы нивелировать вероятность человеческой ошибки. Развертывания должны быть непрерывными и быстрым и процессом, чтобы не замедлять выпуск новых функций или исправление ошибок. Что не менее важно, вы должны иметь возможность быстро откатиться назад или вперёд, если при обновлении возникнут проблемы(SRE практики).

Мониторинг и диагностика имеют решающее значение. Облачные приложения работают в удалённом центре обработки данных, где у вас нет полного контроля над инфраструктурой или, в некоторых случаях даже над операционной системой. В большом приложении нецелесообразно “руками” лесть внутрь виртуальных машин для устранения проблемы или просмотра логов. С услугами PaaS может даже не быть выделенной виртуальной машины для входа. Мониторинг и диагностика дают представление о системе, чтобы вы знали, когда и где происходят отказы. Все системы должны быть наблюдаемыми. Используйте общую и согласованную схему ведения логов, которая позволяет коррелировать события в разных системах.

Процесс мониторинга и диагностики состоит из нескольких этапов:

  • Инструменты. Генерация данных о неработоспособности из логов приложений, журналов веб-серверов, средств диагностики, встроенных в платформу Azure, и других источников.
  • Сбор и хранение. Объединение данных в одно место.
  • Анализ и диагностика. Для устранения проблем и просмотра общего состояния.
  • Визуализация и оповещения. Использование данных телеметрии для выявления тенденций или оповещения операционной группы.
  • Инцидент менеджмент. Чтобы не утонуть в лавине сообщений ранжируйте сигналы, отсеивайте не критичные, обедняйте зависимые, и организуйте быстрое исправление критичных инцидентов.

Руководства по совершенствованию

  • Паттерны проектирования для повышения операционной эффективности
  • Лучшие практики: мониторинг и диагностика
  • Используйте контрольный список DevOps, чтобы проанализировать свой дизайн с точки зрения руководства и DevOps.

Эффективность производительности

Эффективность производительности — это способность вашей рабочей нагрузки масштабироваться для эффективного удовлетворения требований, предъявляемых к ней пользователями. Основные способы достижения этого — правильное масштабирование и реализация предложений PaaS со встроенным масштабированием.

Есть два основных способа масштабирования приложения. Вертикальное масштабирование (масштабирование вверх ) означает увеличение пропускной способности ресурса, например , при использовании большего размера VM. Горизонтальное масштабирование (масштабирование вбок ) добавляют новые экземпляры ресурса, такие как виртуальные машины или реплики базы данных.

Горизонтальное масштабирование имеет значительные преимущества перед вертикальным масштабированием:

  • Невообразимый масштаб облака. Приложения могут быть разработаны для работы на сотнях или даже тысячах узлов, достигая масштабов, невозможных на одном узле.
  • Эластичная горизонтальная мощность. Вы можете просто добавить больше экземпляров при увеличении нагрузки или выводить их в более тихие периоды.
  • Масштабирование может запускаться автоматически по расписанию или в ответ на изменения нагрузки.
  • Горизонтальное масштабирование как правило дешевле, чем вертикальное масштабирование. Запуск нескольких небольших виртуальных машин может стоить меньше, чем одна большая виртуальная машина.
  • Горизонтальное масштабирование также может повысить отказоустойчивость за счёт добавления избыточности. Если экземпляр выходит из строя, приложение продолжает работать.

Преимущество вертикального масштабирования в том, что вы можете сделать это, не внося никаких изменений в приложение. Но в какой-то момент вы достигнете предела, когда вы больше не сможете наращивать мощность. На этом этапе любое дальнейшее масштабирование должно быть горизонтальным.

Горизонтальный масштаб должен быть встроен в систему. Например, вы можете масштабировать виртуальные машины, разместив их за балансировщиком нагрузки. Но каждая виртуальная машина в пуле должна иметь возможность обрабатывать любой клиентский запрос, поэтому приложение должно не иметь “состояния” или сохранять состояние извне (например, в распределённом кэше). Управляемые службы PaaS часто имеют встроенное горизонтальное масштабирование и автомасштабирование. Простота масштабирования этих служб — главное преимущество использования служб PaaS.

Однако простое добавление дополнительных экземпляров не означает, что приложение будет масштабироваться. Приложение может просто упереться узкое место. Например, если вы масштабируете шлюз веб-сервиса для обработки большего количества клиентских запросов, это может вызвать конфликты блокировок в базе данных. Затем вам нужно будет рассмотреть дополнительные меры, такие как оптимистичный параллелизм или разделение данных, чтобы обеспечить большую пропускную способность для базы данных.

Всегда проводите тестирование производительности и нагрузочное тестирование, чтобы найти эти потенциальные узкие места. Части системы с отслеживанием состояния, такие как базы данных, являются наиболее частой причиной узких мест и требуют тщательного проектирования для горизонтального масштабирования. Устранение одного узкого места может выявить другие узкие места в другом месте.

Воспользуйтесь контрольным списком эффективности производительности, чтобы проверить свой проект с точки зрения масштабируемости.

Надёжность

Надёжная рабочая среда — это одновременно отказоустойчивая и доступная рабочая среда. Отказоустойчивость — это способность системы восстанавливаться после сбоев и продолжать работать. Цель отказоустойчивости — вернуть приложение в полностью работоспособное состояние после сбоя. Доступность — это то, могут ли ваши пользователи получить доступ к вашей рабочей нагрузке, когда им это необходимо.

В традиционной разработке приложений основное внимание уделялось увеличению средней наработки на отказ (MTBF). Были потрачены усилия на то, чтобы предотвратить отказ системы.

В облачных вычислениях требуется иной образ мышления по нескольким причинам:

  • Распределенные системы сложны, и отказ в одной точке потенциально может распространиться на всю систему.
  • Затраты на облачные среды остаются низкими за счет использования стандартного оборудования, поэтому следует ожидать случайных отказов оборудования.
  • Приложения часто зависят от внешних сервисов, которые могут временно стать недоступными или ограничивать объемные пользователи.
  • Сегодняшние пользователи ожидают, что приложение будет доступно круглосуточно, без выходных.

Все эти факторы означают, что облачные приложения должны быть рассчитаны на ожидание случайных сбоев и восстановление после них.

Тем не менее, вам по-прежнему необходимо обеспечить отказоустойчивость в своём приложении. Стратегии обеспечения отказоустойчивости можно применять на всех уровнях архитектуры. Некоторые меры по снижению риска носят более тактический характер — например, повторная попытка удалённого вызова после временного сбоя сети. Другие меры по снижению рисков являются более стратегическими, например, переключение всего приложения во вторичный регион. Тактические меры могут иметь большое значение. Хотя перебои в работе всего региона случаются редко, временные проблемы, такие как перегрузка сети, встречаются чаще, поэтому в первую очередь решите их. Правильный мониторинг и диагностика также важны как для обнаружения сбоев, когда они происходят, так и для выявления первопричин.

При разработке гибкого приложения вы должны понимать свои требования к доступности. Какое время простоя приемлемо? Отчасти это зависит от стоимости. Во сколько обойдется вашему бизнесу потенциальный простой? Сколько нужно вложить в обеспечение высокой доступности приложения?

Безопасность

Подумайте о безопасности на протяжении всего жизненного цикла приложения, от проектирования и реализации до развёртывания и эксплуатации. Черезвычайно сильно влияет выбор плтаформы, и “умение ее готовить”. Платформа Azure обеспечивает защиту от множества угроз, таких как сетевое вторжение и DDoS-атаки. Но вам по-прежнему необходимо обеспечить безопасность вашего приложения и процессов DevSecOps.

Вот несколько общих областей безопасности, которые следует учитывать.

Управление идентификацией

Рассмотрите возможность использования Azure Active Directory (Azure AD) для проверки подлинности и авторизации пользователей. Azure AD — это полностью управляемая служба управления удостоверениями и доступом. Вы можете использовать его для создания доменов, которые существуют исключительно в Azure, или для интеграции с вашими локальными удостоверениями Active Directory. Azure AD также интегрируется с Office365, Dynamics CRM Online и многими сторонними приложениями SaaS. Для приложений, ориентированных на потребителя, Azure Active Directory B2C позволяет пользователям аутентифицироваться с помощью своих существующих социальных учетных записей (например, Facebook, Google или LinkedIn) или создавать новую учетную запись пользователя, управляемую Azure AD.

Если вы хотите интегрировать локальную среду Active Directory с сетью Azure, возможны несколько подходов в зависимости от ваших требований. Для получения дополнительной информации см. Наши эталонные архитектуры управления идентификацией .

Защита вашей инфраструктуры

Управляйте доступом к развертываемым ресурсам Azure. Каждая подписка Azure имеет доверительные отношения с клиентом Azure AD. Используйте управление доступом на основе ролей Azure (Azure RBAC), чтобы предоставить пользователям в вашей организации правильные разрешения для ресурсов Azure. Предоставьте доступ, назначив роли Azure пользователям или группам в определенной области. Областью может быть подписка, группа ресурсов или отдельный ресурс. Проверяйте все изменения в инфраструктуре.

Безопасность приложений

В целом передовые методы безопасности для разработки приложений по-прежнему применяются в облаке. К ним относятся такие вещи, как повсеместное использование SSL, защита от атак CSRF и XSS, предотвращение атак SQL-инъекций и т. Д.

Облачные приложения часто используют управляемые сервисы, у которых есть ключи доступа. Никогда не проверяйте их в системе контроля версий. Рассмотрите возможность хранения секретов приложений в Azure Key Vault.

Суверенитет данных и шифрование

Убедитесь, что ваши данные остаются в правильной геополитической зоне при использовании служб данных Azure. В геореплицированном хранилище Azure используется концепция парного региона в одном геополитическом регионе.

Используйте Key Vault для защиты криптографических ключей и секретов. Используя Key Vault, вы можете шифровать ключи и секреты с помощью ключей, которые защищены аппаратными модулями безопасности (HSM). Многие Azure хранения и услуги DB поддерживает шифрование данных в состоянии покоя, в том числе Azure Storage , Azure SQL Database , Azure Synapse Analytics и Космос БД .
